The database design, and how a conversation survives a refresh

01

Two schemas, one database

There isn't one single file that defines every table this project uses. Two different services each create tables in the same Postgres database, for two different reasons — and the code is refreshingly upfront about why.

The first is scripts/schema.sql — the canonical, hand-written, version-controlled schema. It defines users, papers, chunks, requests, and request_retrievals, covered in detail in the companion piece on how the retrieval pipeline works.

Alongside it, the Go gateway defines a second set of tables itself, inside its own source code, and creates them the moment it starts up — no separate file, no migration tool, just a block of CREATE TABLE IF NOT EXISTS statements that runs on every single boot. IF NOT EXISTS is what makes that safe to repeat: the first boot creates the tables, every boot after that finds them already there and moves on.

Why two owners for one database: real back-and-forth conversation — the chat feature itself — was built against this second, Go-owned set of tables before requests/request_retrievals existed in the canonical schema. It hasn't been moved over yet.

Straight from the source — the comment sitting directly above the Go gateway's table-creation code:
"The users & papers schema is owned by scripts/schema.sql (canonical). migrate() only ensures the legacy chat tables still used by the not-yet-migrated chat flow; these are removed in the chat->requests slice."
02

The chat tables, up close

Two tables do the actual remembering. Everything in the rest of this page builds on just these two.

conversations

  • Who it belongs to (nullable — blank for a guest)
  • A title, frozen from your first message
  • When it was started
links to → users · linked from → messages

messages

  • Which conversation it belongs to
  • Who said it — you, or the assistant
  • The text, and — for the assistant's replies only — the sources cited
links to → conversations

A conversation's title is set exactly once — the first 50 characters of the very first message — and never updated again, even if the conversation wanders somewhere else entirely an hour later.

The database does its own cleanup: messages.conversation_id is declared ON DELETE CASCADE. Delete a conversation, and every message inside it disappears automatically — nothing in the application code has to remember to clean them up one by one. It's the same trick a paper's note-cards use elsewhere in this database: delete the parent, and Postgres removes everything hanging off it.
03

A message's journey

Here's exactly what happens, in order, between hitting send and seeing a saved reply.

1

You hit send

The app immediately shows your message and a "thinking" placeholder — it doesn't wait for the network round trip to update the screen.

↓
2

The gateway checks who's asking

An optional login token travels with the request. A valid one resolves to a real user id; no token, or an invalid one, is simply treated as a guest — never a hard rejection.

↓
3

If signed in, the conversation is guaranteed to exist

The very first message of a new conversation creates its row, titled from that message. Every message after that reuses the same conversation id.

↓
4

Your message is saved immediately

Before the assistant has even started answering — so if anything goes wrong generating a reply, what you asked is never lost.

↓
5

The question, plus its working memory, goes to the RAG engine

The same retrieve → rerank → generate pipeline described in the other explainer. What "working memory" means exactly is the next chapter.

↓
6

The reply is saved the same way, sources and all

Only if you're signed in. The cited sources are stored right alongside the reply, not looked up again later.

↓
7

Timing is logged either way

Signed in or a guest, answered or failed — every request's latency lands in a small metrics table that feeds an admin dashboard, entirely separate from the conversation itself.

04

What the AI actually remembers, each turn

This is usually the real question behind "how is chat history persisted" — and the honest answer is more interesting than "it reads the database back."

It's tempting to assume the backend reloads a conversation's full history from Postgres before generating each reply. It doesn't. What actually happens: the browser keeps the visible conversation in its own memory, and right before sending a new question, it takes the last 8 messages — skipping anything still mid-typing — strips out any formatting, trims each one down to 1,500 characters, and sends that whole small bundle along with the new question. Every single time.

The gateway doesn't open that bundle or look anything up because of it — it just relays it, unopened, straight through to the Python engine, which drops it into the prompt as the prior turns of the conversation.

Why a window, and why those two numbers: a conversation could run to hundreds of turns, but a model only ever needs to remember recently enough to resolve something like "turn that into a table" or "make it shorter" — not re-read an hour-old exchange from scratch. Capping both the number of turns and each turn's length keeps every request's size predictable, no matter how long the conversation has actually run.

So Postgres plays the role of the archive — a durable copy kept for later — but the working memory that actually shapes an answer is a short, freshly-rebuilt snapshot of whatever's currently on screen, carried by the browser, not read back out of the database on demand.

05

Loading a conversation back

So what does survive closing the tab, and how does it come back?

The browser's own local storage keeps exactly one small thing: the current conversation's id — not the messages themselves, just a short string under one fixed key. On a page refresh, or when picking an older conversation out of the sidebar, that id is used to ask Postgres for the full transcript, in order, and that becomes the visible conversation again — which also happens to refill the 8-message window described above, ready for whatever gets asked next.

The sidebar itself only ever shows your 5 most recent conversations, newest first, each labeled with that frozen first-message title.

06

Signed in vs. a guest

The assistant works identically either way. What differs is entirely about what gets remembered afterward.

QuestionSigned inGuest
Gets a real answerYesYes
Message saved to PostgresYesNo
Survives closing the tabYes — reload by idNo — gone with the tab
Shows up in the sidebar's last 5YesNo
Can be deleted laterYesNothing to delete
Worth stating plainly: a guest's conversation memory lives and dies with that one browser tab's in-memory state. Nothing about a guest's questions, or the answers they received, is ever written to the database — the assistant still works end to end, there's just no server-side trace of it afterward.
07

Honest state: mid-refactor

A few things worth knowing before treating any of the above as the final design.

Two definitions of "papers" exist in the same database. The canonical schema's papers table (authors, DOI, visibility, ingestion status — see the other explainer) is a different shape from a second, simpler papers table the Go gateway also creates for itself, alongside its own authors, paper_authors, and paper_metadata tables. Only one of these is meant to be the long-term source of truth. This isn't a hidden landmine — it's a project mid-refactor, and the code says so itself.
A seeded placeholder identity. Every time the gateway starts, it makes sure one fixed row exists in users — a fixed all-zero id, with the address recruiter@aether.local. It's used as a fallback "who's asking" wherever an endpoint expects some id but there's no real signed-in user — and it's explicitly excluded from ever owning an actual conversation: that id is swapped for a blank user_id before a conversation is ever saved.
The login token's signing key is a fixed string in the source code today, rather than pulled from configuration. Harmless for a personal project running on one machine; the kind of thing to move into an environment variable before any real person's login is on the line, since it's what ties a saved conversation to the account that's allowed to see it.
08

The full blueprint

The five canonical tables — users, papers, chunks, requests, request_retrievals — are covered in the other explainer. These are the rest: the ones the Go gateway owns for itself.

conversations

  • One row per chat thread
  • Belongs to a user, or nobody

messages

  • One row per turn
  • Ordered by when it was said

papers (Go's own copy)

  • Title, filename, URL
  • A simpler shape than the canonical table

authors / paper_authors

  • Names, and a many-to-many link to Go's papers

paper_metadata

  • A free-form JSON bucket per paper

daily_metrics / query_latency_log

  • Nothing to do with any one conversation
  • Feeds the admin dashboard: request counts, failure rate, p50/p95/p99 latency, one row per day

Word bank

New terms used above that didn't appear in the other explainer.

Cascade delete
A rule on a database relationship that says: delete the parent row, and every row that points to it disappears automatically too.
Idempotent
Safe to run more than once — repeating it produces the same end state instead of erroring or duplicating anything.
JSONB
A Postgres column type that stores a small JSON document directly in a row, instead of forcing it into separate columns.
JWT
A signed token a login handshake hands back, carrying who's logged in so later requests don't need to log in again each time.
Local storage
A small key-value box the browser keeps for a website, which survives closing the tab but never leaves that one browser.
Sliding window (working memory)
Only the most recent handful of turns are carried forward into the next request, rather than an entire, ever-growing conversation.
