Meet Aether — the assistant that reads the papers so you don't have to

Aether is a small program that answers questions about dense computer-science papers on databases and distributed systems, and always shows exactly which passages it used to answer you. This page explains how it works, plain terms first, precise numbers alongside.

01

The big idea

Chatbots are confident writers, but their memory is fuzzy. Ask one a specific question about an obscure paper and it may guess — and say the guess with a completely straight face. That's usually called hallucinating.

Aether avoids that trap by refusing to answer from memory at all. Every time someone asks a question, it first goes and looks the answer up in the actual papers — like a student who opens the textbook to the right page before answering, instead of reciting from memory — and only then writes a response, with the exact passages it used shown right next to the answer, so anyone can check its work.

The fancy name for this pattern is Retrieval-Augmented Generation — RAG for short. Look it up (retrieval), then write about it (generation), with real material in hand the whole time (augmented). Everything below is the machinery that makes that lookup fast, careful, and honest.

02

A question's journey

Here's what happens between typing a question and seeing an answer.

1

You ask a question

e.g. "How does Raft handle a leader crash?" — typed straight into the app.

↓
2

The question becomes a set of coordinates

Your sentence is turned into a list of 1,024 numbers, so it can be compared to every note-card by closeness in meaning instead of matching exact words.

↓
3

A fast first pass finds 20 candidates

A quick search over the whole library returns the 20 note-cards whose coordinates sit nearest to the question's.

↓
4

A slower, careful reader double-checks them

A second model reads the question next to each of those 20 candidates, one pair at a time, and scores how relevant it truly is — catching cases where "nearby on the map" wasn't actually a good match.

↓
5

Only the confident matches survive

Anything scoring below halfway is thrown out. If nothing clears the bar, Aether says so honestly instead of inventing an answer.

↓
6

The answer gets written, sources attached

The surviving note-cards are handed to a language model with instructions to answer using only that material — then the exact passages are shown alongside the answer.

Escape hatch: typing @web-search anywhere in a question tells Aether to also check DuckDuckGo instead of relying only on the papers — this deliberately skips the confidence check in step 5, since a web result isn't being compared to a fixed library.
03

The map of meaning

Step 2 above — "turn the question into coordinates" — is the trick that makes all of this possible. Here's the idea without the jargon.

Aether turns every note-card, and every question asked of it, into a list of 1,024 numbers. Think of it as a very detailed coordinate: instead of just two numbers like a spot on a map (x, y), it's a point in a space with 1,024 directions. Cards about similar ideas land as nearby points; cards about unrelated ideas land far apart. So "find note-cards similar to this question" becomes "find the nearest points on the map."

The gold point is an incoming question. Its three nearest points — all about handling a crashed leader — get pulled as candidates; the storage and consistency clusters, further away, don't.

Grown-ups call this list of numbers an embedding or a vector, and "how close two points are" is called cosine similarity — but the map idea is really all there is to it.

Spec, for the curious: the numbers-machine is BAAI/bge-m3, and it outputs exactly 1,024 numbers per piece of text, normalized so that cosine similarity is just a dot product. It's reused twice in the pipeline: once here, comparing a question to every note-card, and again during ingestion (next chapter) to decide where a paper should be cut into note-cards in the first place.
04

Getting papers into the library

Before any of the above can happen, a paper has to become a set of searchable note-cards. That happens once, when a paper is added.

1

Start with a raw PDF

A dense, multi-column academic paper — e.g. the original Raft paper.

↓
2

Docling reads its structure

An open-source tool called Docling parses headings, paragraphs, and tables — not just raw text — so Aether knows "this sentence sits under the Introduction," not "buried in a table."

↓
3

Cut into note-cards, respecting both structure and meaning

First split along Docling's headings. Then, inside each section, split further wherever consecutive sentences stop being about the same idea — found by comparing their coordinates from the map above. Each card aims for about 512 model-tokens (~380 words), never fewer than 64, and carries forward roughly the last 15% of the previous card so an idea spanning a cut isn't lost.

↓
4

Turn each note-card into 1,024 numbers

The same embedding step described in the previous chapter.

↓
5

File it away with its paper and section

Stored as a row alongside which paper it came from, which heading it was under, and the source filename — used later if that paper is ever removed.

05

Chunking, in depth

Step 3 of ingestion — "cut into note-cards" — is doing more work than it looks. Here's the actual mechanism, why it was chosen over the obvious alternatives, and where it's still rough.

Two passes, not one

The first pass is structural, not semantic. Docling has already parsed each PDF into a tree of real structural elements — headings, paragraphs, list items, table cells — during the earlier parsing step. A tool called HierarchicalChunker walks that tree and produces one raw chunk per structural section, tagging each with its nearest heading. A paper is not a flat wall of text, and an idea in "Evaluation" shouldn't blur into a superficially similar sentence from "Related Work" just because a naive splitter cut across the boundary between them. Anchoring on the document's own organization first rules that out entirely.

The second pass is semantic, and it happens inside each structural section. Every sentence in that section is embedded individually with the same bge-m3 model used at query time. Because those embeddings are normalized, comparing two sentences is just their dot product — so the similarity between every consecutive pair of sentences falls straight out of one calculation. The bottom 15% of those similarity scores, within that specific paper, are treated as natural topic breaks. That threshold is recalculated fresh for every single document — a terse, idea-dense systems paper and a long discursive survey don't get judged against the same fixed number, each is measured against its own rhythm.

A running segment also force-closes once it reaches its 512-token budget, even without a detected topic break, so one structural section can't balloon into a single giant chunk — but only once it's already past a 64-token minimum, so a couple of short sentences right after a real break don't get shipped out as a tiny, context-free sliver. Whatever's left over at the very end of a section gets folded into the previous segment rather than orphaned on its own.

The overlap, concretely

Once segment boundaries are decided, the chunker walks backward through the previous segment's sentences, accumulating them until adding one more would exceed roughly 15% of the token budget (~77 tokens), and prepends that tail onto the next segment. In practice: if a defining sentence sits right at a cut, it appears at the end of one note-card and at the start of the next — so whichever one gets retrieved later, the sentence arrives with its immediate lead-in still attached, not stranded mid-thought.

Every chunk is also stamped with a small header before it's embedded or stored — [Paper: X] [Section: Y]. A sentence like "It achieves this using a randomized timeout" means almost nothing pulled out on its own; the header is what makes a note-card self-describing, for both the search step and for whoever reads it as a cited source later.

Why this, and not something simpler: a fixed-size splitter (every N characters, regardless of content) is the cheapest option and routinely slices mid-sentence, blending unrelated ideas into one blurry chunk embedding. Asking a language model to decide chunk boundaries can produce excellent, context-aware cuts, but costs an LLM call per paper, runs slower, and isn't guaranteed to chunk the same paper the same way twice. This project's approach sits deliberately in between: no new model or external dependency — it reuses the embedding model already resident in memory — fully deterministic on a re-run, and it respects both the document's real structure and its own idea boundaries. The extra compute this costs only has to be paid once per paper at ingestion time, not once per question, which is the entire reason it's affordable: 44 papers get chunked once; thousands of questions get answered against the result.

06

How reranking really works

Step 4 of a question's journey — "a slower, careful reader double-checks them" — is a genuinely different kind of comparison from step 3's fast search. Worth pulling apart.

Two different ways to compare a question and a chunk

The fast first pass (a bi-encoder) embeds the question and every chunk in complete isolation from each other. In fact, all 10,180 chunk embeddings were computed once, back at ingestion time, and never touched again — a search only ever has to embed the question, then let the index find precomputed points that already sit nearby. That separation is exactly what makes it fast enough to search the entire library on every request.

The careful second pass (a cross-encoder) works the opposite way: the question and one specific candidate chunk are fed into the model together, as a single joined input, so its attention mechanism can directly weigh individual words of the question against individual words of that particular chunk before producing one relevance score. That's a comparison a bi-encoder structurally cannot make — squeezing a whole passage down into one fixed-size list of numbers necessarily throws away some nuance (an exact entity match, a negation, "this describes the opposite of what was asked"), and the cross-encoder gets to look at the original words side by side instead of at two already-compressed points.

The cost of that extra care is unavoidable: because the score depends on the question and chunk jointly, nothing about it can be precomputed or indexed the way an embedding can. A cross-encoder score only exists for one specific pairing, and has to be produced fresh, every time. That's exactly why it only ever sees the 20 finalists the fast pass hands it, never the full library — running it against all 10,180 chunks on every question would be far too slow to be usable.

Does it get better "after each use"?

Worth being precise here: the reranker is a fixed, pretrained model. Nothing about answering one question changes its weights, and it does not learn or improve from being used — every single request gets the exact same model doing the exact same kind of comparison. What actually improves is the reliability of the answer, not the model itself, because of one specific property: the reranker's score is trained to be a calibrated relevance probability, not just a rough closeness figure. A bi-encoder's raw cosine distance doesn't have that property — a good match and a mediocre one often land within a hair of each other, so drawing a hard cutoff on distance alone is unreliable. Because the reranker's 0–1 score is meaningfully calibrated, the system can draw one honest line at 0.5 and have it actually mean something. That calibrated score is what lets Aether say "I don't know" instead of guessing — the confidence gate in step 5 only works because this step's output can be trusted as a real probability, not just a proxy for it.

A real path to actual learning-from-usage: this doesn't happen today, but the pieces for it already sit in the schema. request_retrievals already stores, for every past question, which chunks were shown, their rank, and their reranker score. Adding one more column — whether a person marked a given citation as actually useful — would build a dataset of real, domain-specific relevance judgments over time. That's precisely the kind of data used to fine-tune a reranker so it gets sharper on this project's own vocabulary (Paxos, LSM-trees, PACELC) rather than the general web text bge-reranker-v2-m3 was originally trained on. Nothing currently reads that data for training — it's a clear next step, not a current feature.
07

The big move: two filing systems become one

This is the change this page was originally written to explain: where the note-cards and their 1,024-number coordinates live changed, and here's why.

When Aether was new, its note-cards lived in a separate, lightweight filing box called ChromaDB — a tool built specifically for storing text-plus-numbers and searching by closeness. It took about five minutes to set up, which is exactly what you want while you're still experimenting with chunking and proving the retrieval quality works at all. Meanwhile, all the other bookkeeping — who's using Aether, which papers exist, what people asked and when — lived in a completely separate, general-purpose filing cabinet: PostgreSQL ("Postgres"). Two systems, running side by side, that had no idea about each other beyond an ID one of them remembered to pass to the other.

Then
  • ChromaDB — note-cards + their coordinates
  • PostgreSQL — users, papers, questions asked
  • Two things to back up
  • Two things to secure and keep running
  • Links between them kept in sync by hand
→
Now
  • PostgreSQL — everything, including note-cards + coordinates
  • One thing to back up
  • One thing to secure and keep running
  • A note-card can point straight at its paper using the database's own cross-referencing

Once the paper collection settled at a manageable size — 44 papers, about ten thousand note-cards today — the specialized filing box's superpowers (built for millions or billions of note-cards) weren't buying anything. So Postgres was taught the one trick it was missing: storing and searching these number-lists. That's an add-on called pgvector. Every note-card gets copied over, and the second system can be retired.

The honest tradeoff

This isn't a free upgrade. A purpose-built vector database is still the better call at a much larger scale, at very high query volume, or when a project needs features vector databases specialize in. What's being traded here is some of that specialized headroom for a simpler day-to-day life — one database, one backup, one thing to reason about — which is the right trade for a 44-paper library, not a universal rule.

The code keeps that reversible: retrieval is written against a small interface (VectorStore) with two implementations — one for Chroma, one for pgvector — chosen by a single setting. If the library ever outgrows Postgres, only that one piece needs to change, not the rest of the app.

How the move itself happens

A one-time script reads every note-card out of the old ChromaDB collection, 500 at a time, and inserts it into the new chunks table, then compares the final counts on both sides before declaring success. Nothing about the original Chroma files is touched or deleted in the process.

Where things stand today: the pgvector path, the schema, and the migration script all exist and are being wired in on this branch. The switch between the two — an environment setting called VECTOR_BACKEND — still defaults to the old Chroma path in each environment until that environment's migration has been run and its row counts verified. Flipping it to pgvector is the actual cutover moment; flipping it back is the rollback plan, since the old data is left in place rather than deleted.

Why the careful reader runs on a regular processor, not the graphics card: the development machine's graphics card has about 3.6 GB of memory, and the embedding model alone nearly fills it. Rather than fight over that space, the careful-reader step runs on the CPU instead — which is fine, because by the time it runs there are only 20 candidates left to read, not the whole library.
How the system watches itself: two separate tools split the job — one watches the plumbing (how long a search took, how many candidates survived the confidence check), the other watches the AI model's own reasoning (which prompt, which model, how many tokens). They're kept strictly apart on purpose, but every request carries one shared ID end to end, so a single question can still be traced through both.

The blueprint

Five tables now live in the one database. Here's what each one remembers, in plain words.

users

  • Who's allowed in
  • Login count, last login
  • How many papers/questions they've submitted

papers

  • Title, authors, where it came from
  • Whether it's curated or a user upload
  • How ingestion is going (pending → done)
linked from → chunks, requests

chunks

  • The note-card's text
  • Its 1,024-number coordinate
  • Which paper & section it's from
links to → papers

requests

  • The question asked
  • The answer given, and by which model
  • How long it took
links to → users

request_retrievals

  • Which note-cards fed a given answer
  • Their rank and confidence score
  • Kept even if the paper is later deleted
links to → requests, papers
An honest leftover: the request_retrievals table still names its reference column chroma_chunk_id — a naming fossil from before the move. It now stores an ID from the Postgres chunks table. Renaming it is a tidy-up, not a correctness issue, so it's still on the list rather than done.

Scaling to a billion users

"Bigger" means two different things here, and they break the system in different places: far more people asking questions (query traffic), and far more papers being indexed (corpus size). Most of a RAG system's cost is either cacheable (repeated questions) or already handed off to an external, independently-scaled provider (the LLM call) — so this is mostly a well-trodden scaling story of replicas, caches, and sharding, not a novel one.

1

Today — one machine, everything on it

One Postgres, one Python process holding both models in memory, one Go gateway. Nothing is the bottleneck yet, because nothing is under load.

↓
2

Thousands of concurrent users

The single Python engine process becomes the first limit — it runs retrieve → rerank → generate synchronously per request, and the CPU-bound reranking step starts to queue. Fix: run several stateless replicas of the Go gateway and the Python engine behind a load balancer. Because retrieval already sits behind a small interface and nothing holds per-user state in memory, this is an infrastructure change, not a rewrite.

↓
3

Millions of concurrent users

The single Postgres instance becomes the limit — both ordinary lookups and vector search compete for the same reads, and a large share of questions are near-duplicates of each other. Fix: add Postgres read replicas, put a connection pooler in front (a fleet of engine replicas each holding their own pool doesn't scale cleanly against raw Postgres connections), and add a cache in front of the whole pipeline keyed by the question, so a repeated question skips retrieval and generation entirely.

↓
4

Billions of requests, and/or the corpus itself reaching millions of documents

This is where the earlier tradeoff reverses: a single-node index sized for ~10K vectors doesn't extend cleanly to tens of millions on one machine — build time and memory both grow substantially, and one node caps how much query load it can absorb no matter how it's tuned. This is exactly the point where a purpose-built, horizontally-shardable vector store (or a sharded pgvector deployment, splitting the corpus across many nodes and fanning a query out to all of them) starts winning again — and exactly why retrieval was kept behind that small interface: swapping the storage engine here doesn't require touching the rest of the app.

↓
5

Ingestion at the same scale

If the corpus is also growing, not just the user count, the local batch scripts run by hand against a folder of PDFs stop being adequate. That work moves to a queue: new PDFs land in object storage, a queue fans them out to a pool of parsing/embedding workers, autoscaled by queue depth. A sketch of exactly this kind of pipeline already exists, if aspirationally, elsewhere in this project's own architecture notes.

↓
6

The answer-writing step

Gemini and Groq are already hosted, already-scaled external services, so the bottleneck shifts from infrastructure to rate limits and unit cost. At real billion-request volume that usually means negotiated enterprise quota, an additional fallback provider, and/or self-hosting an open model on a dedicated GPU cluster for the highest-volume traffic, keeping the external providers as overflow.

↓
7

Multi-region

A billion users aren't in one place. The natural next step is regional read replicas of both the metadata and the vector index, plus a CDN/edge layer in front of the UI and cached answers — with writes (new papers, new accounts) still converging on one primary region.

13

Word bank

Every technical term used above, in one place.

Bi-encoder
A model that embeds two things separately and compares the results afterward — fast, but the two things never directly interact.
BM25 / hybrid search
An exact keyword-matching search technique, sometimes blended with vector search so specific terms aren't only findable "by meaning."
Calibrated score
A score trained to actually mean what it says — a 0.8 really is more relevant than a 0.4 — as opposed to a raw number that's merely ranked correctly.
Chunk
A small, self-contained slice of a paper — a "note-card."
Connection pooler
A layer in front of a database that shares a small set of real connections across many client processes, instead of each one opening its own.
Cosine similarity
A way of measuring how alike two coordinate-lists are, based on the angle between them.
Cross-encoder / reranker
A model that reads a question and one candidate together, rather than comparing coordinates from a distance — slower, but more careful.
Docling
An open-source tool that reads a PDF's structure — headings, paragraphs, tables — not just its raw text.
Embedding / vector
A list of numbers representing the meaning of a piece of text, so meaning can be compared mathematically.
Extension (Postgres)
An add-on that teaches a standard database a new trick — here, storing and searching vectors.
Foreign key
A database's built-in way of saying "this row belongs to that row," enforced automatically.
HNSW index
The specific technique pgvector uses to find "nearest points" quickly without checking every single one.
LLM
Large language model — the kind of AI model that writes the final answer.
RAG
Retrieval-Augmented Generation: look it up, then write about it, using only what was found.
Read replica
A copy of a database that only serves lookups, freeing the main copy to focus on writes.
Sharding
Splitting one large collection across several machines, each holding a slice of it.
Token
A model's unit of text — roughly three-quarters of a word, on average.
Threshold gate
A cutoff score below which a result is discarded rather than trusted.
